# RAG-KW 智能知识库系统产品手册

## 1. 系统简介

RAG-KW 是一个基于 Spring Boot 3.3 的企业级智能知识库问答系统，采用 RAG 检索增强生成技术，把私有文档转化为可问答的知识库。系统覆盖文档上传、智能切分、向量化、混合检索、流式生成的完整流水线，支持 MySQL、Elasticsearch、Redis 三存储协作。整体架构分为客户端层、API 网关层、业务逻辑层和数据存储层，业务逻辑层由文档服务、RAG 问答服务、记忆管理服务、对话日志服务和向量化服务组成，各服务职责单一、通过依赖注入解耦，方便单元测试与扩展。系统既适合企业内部知识沉淀，也可以作为智能客服和个人学习助手的底座，代码采用 Java 17 编写，工程结构清晰，具备 Docker 化交付能力。项目最初只实现了基础 RAG 问答，后续逐步引入混合检索、三层记忆和 Agent 工具调用，每一轮演进都有明确的设计目标与评估手段，体现了持续迭代的工程思路。

## 2. 支持的文档格式

系统支持上传 PDF、Word（DOC 与 DOCX）、Excel、TXT 等常见办公文档格式，单文件大小上限为 50MB。PDF 解析由 Apache PDFBox 完成，Office 文档由 Apache POI 完成，上传接口为 multipart 表单，支持批量解析与格式校验，解析失败会返回明确错误信息并记录日志。文档内容解析后会抽取纯文本、页数和文件大小等元数据，供后续分块与展示使用；Excel 会按单元格顺序拼接文本，尽量保留表格语义；TXT 则按 UTF-8 编码读取，兼容中文内容。格式解析层通过统一接口抽象，新增文件格式只需实现解析器并注册，无需改动上层流程。不同格式解析出的文本还会经过清洗，去掉控制字符与多余空白，避免污染向量化和检索结果，这也是容易被忽视但影响很大的工程细节。

## 3. 文档入库流程

文档上传后先计算文件内容 MD5，命中已有记录时直接返回已入库任务，实现秒传去重，避免重复解析和重复向量化。新文档则创建异步处理任务：解析文件内容、智能分块、批量向量化，最后把元数据写入 MySQL、把向量切片写入 Elasticsearch，并通过 Redis 实时更新处理进度，前端可以按任务 ID 轮询查看解析、向量化各阶段的完成百分比。异步任务使用 Spring 的 @Async 机制执行，与主请求线程解耦；批处理每批 50 条文本调用一次 Embedding API，兼顾吞吐与限流；任务失败时自动进入清理流程，删除半成品数据并更新任务状态为失败，保证系统不会残留脏数据。入库链路中的每一步都有状态记录与耗时统计，便于定位瓶颈，比如解析慢还是向量化慢，这为后续性能优化提供了数据基础。

## 4. 三层记忆架构

系统实现了三层记忆架构。短期记忆存放在 Redis，保存当前会话最近 10 条对话，TTL 默认 7 天，用于维持多轮对话上下文；长期记忆存放在 MySQL，永久保存全部对话记录，支持历史回溯与统计；语义记忆存放在 Elasticsearch，保存对话摘要向量，支持基于语义的智能回忆。三层记忆各司其职，兼顾速度、持久化和语义相关性。读取时优先从 Redis 获取近期对话，Redis 未命中时自动从 MySQL 恢复会话再写回缓存，形成两级缓存回源链路；写入时同步落 Redis 与 MySQL，并异步调用 LLM 生成对话摘要存入 ES，摘要检索与知识库检索走同一套向量检索基础设施，降低系统复杂度。记忆设计回答了一个经典问题：多轮对话中上下文到底存哪里、存多久、怎么找回，把缓存的时效性与持久化的可靠性结合了起来。

## 5. 混合检索与 RRF 融合

检索支持纯向量、纯关键词、混合三种模式，通过配置项 rag.retrieval.mode 切换。纯向量模式使用 kNN 相似度搜索，适合语义相近但用词不同的提问；纯关键词模式使用 BM25 全文检索，配合 IK 中文分词，适合精确术语匹配；混合模式通过 RRF 算法融合两种结果，兼顾语义理解与精确匹配，默认返回 top-5 个相关片段。RRF 融合不依赖分数归一化，对两种检索的打分尺度差异不敏感，工程上更稳健；系统还支持配置 numCandidates、RRF 窗口大小、排序常数等参数。检索层被抽象为独立的 RetrievalService，普通 RAG 问答、Agent 工具调用和检索评估共用同一套代码，保证线上与评测口径一致。为了验证混合检索确实优于单一模式，系统内置了检索评估模块，用统一测试集对比三种模式的召回率与排序质量，用数据而不是直觉驱动方案选择。

## 6. 流式输出与交互体验

问答接口基于 SSE 实现流式输出，模型生成过程中即可向用户推送内容，显著降低首字延迟，提升交互体验。系统同时提供普通问答和流式问答两套接口，普通接口适合服务端调用与测试，流式接口适合前端实时展示。流式事件包含消息增量与完成标记，前端可据此实现打字机效果。SSE 连接超时设置为 120 秒，避免长任务挂起；服务端通过流式订阅逐段转发模型输出，同时累计完整答案用于后续存档，兼顾实时性与数据完整性。流式实现基于 SDK 的 Flowable 响应式流，配合 Spring 的 SseEmitter，代码简洁且便于扩展事件类型。Agent 模式下流式事件进一步细分：工具调用事件、工具结果事件与最终答案事件分别推送，前端可以展示模型"先查资料再回答"的完整过程，这对理解 Agent 行为非常有价值。

## 7. 部署方式

系统支持 Docker Compose 一键启动 MySQL、Elasticsearch、Redis 和应用容器，也支持直接运行 JAR 包部署到生产环境。项目提供 start 启动脚本与 Dockerfile，健康检查接口暴露在 Actuator 的 /actuator/health，配合容器健康探针可以快速验证服务状态，环境差异通过环境变量隔离。docker-compose.yml 中定义了各服务的端口、数据卷、资源限制和依赖顺序，启动时先拉起存储服务再启动应用，避免连接失败导致启动中断；生产部署建议将 Elasticsearch 独立部署并配置数据持久化卷，MySQL 通过主从或云数据库保障高可用，Redis 配置持久化策略防止缓存丢失。整体部署方案强调开箱即用与生产可用之间的平衡，本地一条命令即可跑通全链路，方便演示与二次开发。

## 8. 配置管理

环境配置通过 .env 文件管理，包括 LLM API Key、模型名称、Embedding 模型与维度、检索模式、检索数量等参数，项目提供 .env.example 模板方便初始化。配置项支持默认值，未设置时使用内置默认配置，保证本地开发零配置启动；敏感信息通过环境变量注入，避免硬编码。Spring 配置采用分层覆盖原则：application.yaml 提供默认值，环境变量通过占位符覆盖，容器编排时按环境注入不同配置。所有与模型相关的配置集中在 llm 前缀下，记忆与检索配置分别使用 memory 和 rag 前缀，Agent 与评估模块新增配置也沿用相同风格，保证配置可发现、可审计。配置管理中比较关键的一点是默认值策略：新模块必须带默认值上线，避免配置文件缺项导致启动失败，同时把可选功能开关独立成布尔配置，比如长期记忆开关与演示数据清理开关。

## 9. 文本分块策略

文本分块采用递归分块策略，优先按段落、再按中英文句子、最后按标点符号逐级切分，并支持 100 字符重叠，最大程度保证 chunk 语义完整性。分块器还做了文本归一化处理，合并过小的碎片，避免产生无意义切片。分块质量直接影响检索效果，因此系统把分块策略作为可调参数，配合评估集验证效果。递归分块的核心思想是粗粒度优先：先尝试按空行切分，段落仍超长时降级到句子分隔符，再不行就按标点切，最后才强制截断，每一层都尽量保留语义边界；重叠机制让相邻 chunk 共享边界信息，减少上下文断裂导致的召回丢失。分块参数比如最大长度、最小长度与重叠长度都提取为常量并写入文档，面试与评审时可以清楚解释每个参数为什么这么选。

## 10. API 接口说明

系统提供文档上传、进度查询、普通问答、流式问答等 REST 接口，接口路径与参数说明见 API.md 文档。问答接口支持 userId 与 sessionId 参数，用于多租户隔离与会话管理；文档接口返回任务 ID，进度接口返回当前步骤与完成百分比，便于前端做上传进度条。除基础 RAG 接口外，系统还提供 Agent 问答接口与检索评估接口：Agent 接口支持工具调用轨迹回传，评估接口返回各检索模式的对比指标与 Markdown 表格。所有接口统一返回 JSON，错误通过 HTTP 状态码与错误信息区分，文档接口通过 OpenAPI 风格说明请求参数、响应结构与示例，降低接入成本。接口设计遵循一个原则：能用查询参数就不用请求体，能用 SSE 就不轮询，接口职责单一，前端与测试同学按文档即可完成联调。

## 11. 事务一致性与容错

由于 Elasticsearch 不支持 Spring 事务，系统对 ES 与 MySQL 双写采用手动回滚补偿机制：先写 MySQL 元数据，再写 ES 向量，任一步失败都会触发回滚清理，防止脏数据。异步任务失败时自动清理 Redis 进度、MySQL 元数据和 ES 中残留的分块，同时记录失败原因，保证系统自愈能力。补偿逻辑采用显式 try-catch 与步骤标记实现，每一步成功后才推进，失败时按逆序撤销已写入的数据，比分布式事务框架更轻量且可控。对话保存同样遵循先主后次的顺序，即便记忆写入失败也不影响主流程回答返回，日志记录完整链路便于排查。这个设计也常被面试官追问：为什么不引入消息队列或事务消息，回答是当前规模下补偿机制复杂度更低、可解释性更强，等到写入成为瓶颈再引入 MQ 做异步削峰。

## 12. 应用场景

系统适用企业知识库、智能客服、个人学习助手、文档搜索引擎等场景。企业内部可以把制度文档、产品手册、运维手册导入系统，员工用自然语言提问即可获取带出处的答案；客服场景接入用户问题后自动检索产品文档并生成回答，显著降低人工成本；个人用户则可以把学习资料整理成可检索的知识库。在智能客服场景中，系统还支持与 Agent 工具调用结合：模型先判断问题是否涉及知识库，再决定检索策略，需要多份文档对比时自动执行多次检索并汇总，实现从被动问答到主动规划的升级，这也是 RAG 系统向 Agentic RAG 演进的核心方向。后续计划把知识库检索封装成 MCP 工具对外暴露，让外部 Agent 也能复用这套检索能力，进一步扩大系统的应用边界。
